# Specialist Onboarding Protocol

This protocol applies to every newly created Design Studio specialist chat, including future specialties not yet represented in the repository.

## Rule 1 — Read before creating a new canonical structure

A newcomer must first understand the existing studio before creating a new specialist directory, status file, or canonical ownership claim.

Read in this order:

1. `AGENTS.md`
2. root `README.md`
3. `progress/STATUS.md`
4. every existing specialist status file under `progress/`
5. `research/README.md`
6. relevant domain README files under `research/`
7. `coordination/COLLABORATION_PROTOCOL.md`
8. relevant existing research discovered through search
9. `curriculum/MASTER_CURRICULUM.md` when the proposed role affects learning gates

The newcomer may analyze or discuss overlapping topics during onboarding. The restriction applies to creating a conflicting **canonical specialist structure**, not to learning.

## Rule 2 — Map existing knowledge and overlap

The newcomer must search for concepts adjacent to its proposed specialty and answer:

- Which current specialist already owns canonical knowledge related to this problem?
- Which existing studies can be reused directly?
- Which studies deserve independent verification, replication, challenge, or transfer testing from the new specialty's perspective?
- Where would a new specialist create confusing ownership if boundaries are not clarified?
- What important questions are genuinely underdeveloped or methodologically distinct?
- Would the role add enough unique expertise, project value, methods, or validation capability to justify a dedicated specialty?

Overlap is expected in mature design disciplines and is not itself a defect.

## Rule 3 — Submit an onboarding report

Before creating a new specialist structure, provide the user/coordinator with:

### Proposed role

Name of specialty and its purpose.

### Primary ownership

Questions for which this role should become the canonical specialist.

### Shared / overlapping territory

Topics that legitimately overlap Type, Color, Layout/Interaction, or another specialist.

For each overlap, state whether the expected relationship is:

- reuse;
- independent replication;
- method comparison;
- adversarial review;
- transfer validation;
- project collaboration.

### Existing evidence to inherit

Canonical files from current specialists that this role will use, test, or extend.

### Unique contribution

What distinct expertise, methods, validation capability, or project value justifies the role.

### Collaboration interfaces

What this specialist expects to receive from others and what it expects to hand back.

### Proposed repository structure

- canonical research path;
- specialist status path;
- unique study-ID prefix;
- any exercise/artifact paths required.

### Initial research agenda

The first questions that would materially improve Design Studio's capability. They do not need to be completely non-overlapping if independent validation or a new disciplinary perspective is the point.

## Rule 4 — Approval before canonical repository mutation

The newcomer waits for explicit user/coordinator approval before:

- creating a new canonical research directory;
- creating a specialist status file;
- assigning itself a prefix;
- moving or reclassifying existing evidence;
- claiming canonical ownership of an existing topic.

Once approved, the coordinator updates `AGENTS.md`, `README.md`, `research/README.md` and `progress/STATUS.md` as needed.

The newcomer does **not** need approval merely to read, reason about, critique, or independently investigate overlapping material inside the conversation.

## Rule 5 — Inherit all studio governance

A newly approved specialist follows the same rules as existing specialists:

- authoritative evidence over trend summaries;
- SOURCE / SYNTHESIS / STUDIO JUDGMENT / OPEN / DEPENDENCY distinction;
- mandatory cross-domain scan before substantial work;
- `RELATED DOMAIN CHECK` in new studies;
- `HANDOFFS TO OTHER SPECIALISTS` after studies when useful;
- purposeful overlap allowed and documented;
- no meaningless repetition for file accumulation;
- own-path/own-status writing boundaries during ordinary work;
- no silent overwriting of disagreements;
- persistence to GitHub after substantial completed work;
- no PASS or mastery claim from reading alone;
- project usefulness as the final objective.

## Newcomer checklist

A newcomer is ready for canonical specialist activation when all are true:

- [ ] Existing specialist boundaries are understood.
- [ ] All current specialist statuses have been read.
- [ ] Related research has been searched.
- [ ] Reusable evidence has been identified.
- [ ] Useful replication/challenge opportunities have been identified where relevant.
- [ ] Overlap risks and collaboration opportunities have been documented.
- [ ] Primary ownership and unique contribution have been defined.
- [ ] Canonical path and prefix have been approved.
- [ ] Collaboration interfaces are explicit.
- [ ] The initial research agenda has clear professional or project value.

The aim is not to force specialties into non-overlapping boxes. The aim is to keep canonical ownership intelligible while allowing serious interdisciplinary research.
