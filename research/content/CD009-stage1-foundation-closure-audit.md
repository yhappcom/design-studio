- retry safety is unknown;
- asynchronous outcome is ambiguous;
- information architecture is broken;
- layout cannot accommodate necessary meaning;
- accessibility delivery is behaviorally incorrect.

CD008 specifically refuses `Failed. Retry` when outcome is unknown because that is a product-state/recovery issue, not a tone problem.

## 8. Foundation project-readiness check

A Foundation topic is professionally useful only if the specialist can answer practical project questions.

### When should the knowledge be used?

Now answerable for terminology, actions, state messages, minimum-sufficient instructions, accessibility-oriented wording and localization-ready source content.

### When should it not be used mechanically?

Now answerable: avoid full metadata/process overhead for trivial strings; avoid using wording to repair broken product contracts; avoid plain-language simplification that destroys expert-domain distinctions.

### What inputs are required?

Now answerable: object/concept map, state/action/recovery contract, audience/domain evidence, consequence/persistence, platform/context and localization assumptions.

### What concrete decision changes?

Now answerable: naming, labels, state-message separation, helper text, information order, string-key identity, escalation to peer domains.

### What alternatives/trade-offs exist?

Demonstrated in CD008 through minimal-command, explanation-heavy and state/decision architectures.

### What failure modes exist?

Documented across CD001–CD008 and integrated in CD008.

### Which peer evidence is needed?

Demonstrated explicitly across Type, Color, Layout/Interaction and Web.

### How should the result be validated?

Now answerable through staged non-human semantic audit → implementation transfer → localization/RTL stress → domain review → human testing when appropriate.
