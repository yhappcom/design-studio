# T075 — LogMate Large-Text Ledger Type Adaptation

Status: **PRACTICE / TRANSFER VALIDATION — no Type gate promotion**

## PURPOSE
Resolve the Type side of LogMate H2: dense operational ledgers must remain readable and comparable under enlarged text without using immature custom drawing, semantic abbreviation, negative tracking, or kerning as a rescue mechanism.

## RELATED DOMAIN CHECK
- Type: T021 drawing gate and T074 signature role contract checked; widths/sidebearings remain frozen and kerning OFF.
- Color: C105 functional salience must survive reduced chrome and alternate color modes.
- Layout/Interaction: I092/L096 local semantic calibration and cross-surface recovery constraints checked.
- Web: W105 production/served/independent-engine ladder checked.
- Content: CD111 protected wording and semantic economy checked.
- W3C WCAG 2.2 Reflow/Text Spacing evidence checked through current official WAI guidance.

## SOURCE
WCAG 2.2 SC 1.4.10 permits two-dimensional layout exceptions for data tables/grids where the relationship is required for meaning, but the exception is scoped: surrounding content should reflow and individual cell content still requires appropriate handling. SC 1.4.12 requires no loss of content/function when specified text spacing is overridden.

## PRACTICE — TYPE ADAPTATION ORDER
For dense LogMate ledger rows, apply this order before considering truncation:
1. preserve semantic field identity and canonical source string;
2. use mature production/fallback metrics, not T021 provisional metrics;
3. preserve SC-B role separation: authored UI proportional, bounded operational comparison mono/tabular where justified;
4. allow row height and local vertical rhythm to grow;
5. allow low-priority descriptive cells to wrap where meaning survives;
6. move secondary metadata to a disclosure/detail representation when the complete value remains available;
7. truncate only with an in-context reveal mechanism and never for ambiguity-critical operational identifiers unless separately proven safe.

Forbidden rescue tactics: negative tracking, glyph narrowing, font-size suppression that defeats enlargement, semantic shortening solely for fit, or kerning before drawing/general-spacing closure.

## CRITIQUE FIXTURE
Stress every future ledger concept with:
- Date: canonical numeric order plus longest supported locale-order representation fixture;
- Flight: wide carrier + 4-digit number + suffix and narrow carrier comparison;
- registration: long realistic identifier;
- DEP/ARR: paired airport identifiers;
- duration: ordinary H+MM and cumulative 99,999+59;
- long English recovery/status string;
- arbitrary Unicode Remark/source text;
- baseline, 200% text enlargement, and WCAG text-spacing override.

Reject a concept if comparison survives only because a fixture is shortened, a font is squeezed, or user/source text is hidden without recovery.

## SYNTHESIS
Large-text ledger adaptation is not a font-size problem. It is a negotiated Type+Layout representation problem: preserve semantic identity and comparison roles first, then allow geometry to adapt. The two-dimensional nature of a professional ledger can justify local scrolling, but not clipped cell text or frozen provisional metrics.

## OPEN

- Exact production proportional/mono/fallback stack.
- Rendered 200% and text-spacing specimens in production Web build.
- Native/iPad transfer and human scan/comparison evidence.

## HANDOFFS TO OTHER SPECIALISTS
- Layout/Web: use the adaptation order as a rejection ladder before inventing compact typography.
- Content: preserve canonical values; disclosure may change placement, not truth.
- Color: enlarged/reflowed states must retain focus/error/recovery salience without depending on compact row chrome.
